# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Open-source screening tool for scoping reviews (JBI) and systematic reviews, built as a native macOS app (Rust core + Tauri 2 + React). There is no server: team members exchange signed files. All project prose is **German**: code comments, docstrings, UI strings, error messages, docs, CI step names and commit messages. Keep new text German. The app itself is bilingual (German, English): the German text in the source is the key, translations live in catalogues (see `i18n.rs` below), and every new user-facing text needs its English entry.

`docs/umsetzungsplan.md` is the current plan (milestones 0–11; 0 to 9 are done, except writing back to Zotero) and `docs/review-workflow.md` the workflow it implements. `docs/anforderungsanalyse.md` holds requirements, the stage model, the event catalogue and the plan, including the decision for the Mac app (section "Entscheidung: native Mac-App mit Austauschdateien"). The README lists deviations from the plan and open decisions.

## Commands

Rust comes from Homebrew's keg-only `rustup`; if `cargo` is not on PATH, use `export PATH=/opt/homebrew/opt/rustup/bin:$PATH`.

```bash
cargo test -p ort-core                         # all core tests
cargo test -p ort-core --test flow             # one test file (eventlog, projections, agreement, importers, exchange, flow, workflow)
cargo test -p ort-core gap_in_chain            # single test by name
cargo test -p ort-core --release --test bench -- --ignored --nocapture   # timings with 20,000 records
cargo fmt --all --check                        # rustfmt.toml: max_width 120
cargo clippy --workspace --all-targets -- -D warnings

cd app
npm install
npm run typecheck
npm run tauri dev                              # runs Vite on 127.0.0.1:5173 and the app
npm run tauri build -- --bundles app           # unsigned .app in target/release/bundle/macos/
```

A second identity on the same machine (for trying the exchange): `ORT_DATA_DIR=/tmp/x ORT_KEY_STORE=file npm run tauri dev`.

End-to-end in a browser against the real core (development bridge, feature `bridge`, never in a release build): one bridge per person, e.g. `ORT_BRIDGE_PORT=5181 ORT_DATA_DIR=/tmp/ort-a ORT_KEY_STORE=file cargo run -p open-review-tool --features bridge`, then `npx vite` in `app/` and open `http://127.0.0.1:5173/?bridge=5181`. `app/src/dev/bridge.ts` forwards every command over HTTP; file dialogs take the next path from `window.__ortPicks` (for scripts) and "save" writes into `<ORT_DATA_DIR>/out` (listed in `window.__ortSaved`); confirmations are answered with yes. `ORT_KEY_STORE=file` keeps the private key in `identity.key` instead of the macOS Keychain; use it for tests so the Keychain is not touched.

Agreement reference values live in `crates/ort-core/tests/fixtures/agreement.json`, generated by `make_agreement_fixtures.py` (needs numpy and scikit-learn). Regenerate only if the reference scenarios change.

## Architecture

**Event log is the source of truth for decisions.** Every decision is a signed, append-only event in a per-review SQLite file (`reviews/<review_id>.ortreview` in the app data dir). Bibliographic records, import batches, stage assignments and display names are ordinary tables; records and assignments are protected by digests (`records_sha256` in `RecordsImported`, `record_ids_sha256` in `StageInstanceOpened`). Names live only in the deletable `person` table; the log holds pseudonymous `actor_id`s.

- **Chains per person and stream**, not per review: each actor has a `main` stream (management, consensus) and one `stage:<id>` stream per stage for `VoteCast`/`VoteRevised`/`RecordFlaggedUndecidable` (`event::is_blindable`). This lets a package drop a blinded stage's foreign votes as whole chains without gaps. Don't move blindable events into `main` or vice versa.
- Hash = SHA-256 over canonical JSON (`canonical.rs`, RFC 8785) of the envelope without `hash`/`signature`; signature = Ed25519 over the hash. **Floats are rejected in payloads**; keep payload numbers integral.
- `catalog.rs` is the single registry of event types: a human label (`catalog::label`, catalogue key „Ereignis: …“), chain (`main` or `stage`), who may write, stage rule, payload check, and `upcast` for older payload versions. A new event type needs one entry there and no other list. `Review::append` validates before appending; `exchange::authorize` validates on merge and rejects single events. Projections read old payloads through `catalog::upcast`, never by changing the stored event.
- Table changes go into `MIGRATIONS` in `store.rs` (append only, tracked in `PRAGMA user_version`). Bundles carry `FORMAT_VERSION` 2; identity files stay at `IDENTITY_VERSION` 1.
- `store.rs` is the only write path (`Store::append` signs and chains; `insert` for already-verified foreign events). Triggers abort UPDATE/DELETE on `event`.
- Ordering across people uses `projection::order_key` (`occurred_at`, `actor_id`, `stream`, `seq`); within a chain always `seq`. `append` keeps `occurred_at` monotonic per actor. "First `StageInstanceOpened` wins" fixes stage rules.

**Layers in `crates/ort-core`** (pure library, no Tauri):
- `projection.rs`: `ReviewState` (title, members with public keys, criteria, stage order) and `StageState` (current votes, consensus, flags, `final_decisions`) computed from events on every call; nothing is cached or stored.
- `workflow.rs`: templates (`templates/*.json`, embedded) and `Workflow`, built from `WorkflowVersionPublished`, `GateEvaluated` and `GateOverridden`. The chosen template is copied into the log at creation; reviews without that event fall back to the built-in `free` template (`version` 0), which blocks nothing. `Workflow::stations` computes each station's state (`locked`/`open`/`running`/`done`), rounds and checks. A station with a non-empty `gate` blocks all later stations until its gate passes or is overridden with a reason. Station kinds are `setup`, `screening`, `form`, `report`; `available` says whether this app version can work a station. Terms shown in the UI (`records`, `sources`) come from the template, not from code. Built-in templates (`BUILTIN`, in the order offered at creation): `jbi_scoping`, `rapid_review` (Cochrane 2024: dual pilot with 80 % agreement, then `single_verified` for screening and extraction, risk of bias as fields of the extraction form, no checklist), `state_of_the_art` (one vote, no gates) and `free`. A new template that needs no new station kind, check or tool is one JSON file plus its entry in `BUILTIN`.
- Stage rules live in `StageInstanceOpened` (schema version 2: `station`, `round`, `decision_rule`, `conflict_rule`, `verify`) and are fixed once opened. `StageState::final_decisions` implements `unanimous`, `liberal`, `single_verified`; `wants_vote_from` decides what `next_record` offers. `single_verified` stages are never blind. With `conflict_rule = third_person`, `record_consensus` and `exchange::authorize` reject a consensus from someone who voted on that record. `close_stage` evaluates the station's gate and appends `GateEvaluated` (integers only: numerator, denominator, `percent_x100`).
- `criteria.rs`: `Criteria` is a list of `Criterion { code, element, kind, text, note }` plus `guidance` and keywords (`CriteriaVersionPublished` schema version 2; version 1 free text is upcast to one criterion without code, old free reasons become exclusion criteria whose code is the old wording). Exclusion reasons are the codes of the exclusion criteria. A stage shows and checks the criteria version it was opened with (`service::stage_criteria`, `ReviewState.criteria_versions`). `check_reasons` is the single rule for `primary_reason` and `reasons`: `cast_vote` and `record_consensus` always apply it, `exchange::authorize` applies it for stages with `reason_required` (set from the template station, e.g. `fulltext`), where every exclusion needs exactly one primary reason.
- `search.rs`: `Searches` built from `SearchVersionPublished` and `SearchPeerReviewed`. One search per source (`search_id`) with versions; an import (`RecordsImported`, schema version 2) names `origin` (`catalog::ORIGINS`) and optionally `search_id` + `search_version`. `exchange::authorize` rejects an import or peer review naming an unknown search version. `Review::import_summary` counts hits per source and duplicates from the log alone.
- `duplicates.rs`: fuzzy duplicate candidates are a projection (`candidates` over `Store::record_keys`, never stored); only decisions are events (`DuplicatesResolved`, up to `catalog::MAX_PAIRS` pairs, last decision per pair wins). `Resolutions.removed` maps a removed record to the one kept. "Active" records are those with `duplicate_of IS NULL` (exact match at import) that are not in `removed`; `open_stage` (all scopes), `facts`, `detail` and `records` use that, existing stages never change. The setup checks `search_documented` and `no_unresolved_duplicates` gate the pilot in the JBI template; candidates are only computed when the template asks for that check.
- `fulltext.rs`: full texts live outside the app, in a linked folder or in Zotero. `FullTextStatusSet` (main chain, any writer) holds `retrieved` (origin `folder` + relative path, or `zotero` + attachment key, plus `sha256` and `size`), `unavailable` (with reason) or `open`; last event per record wins. The folder location is a local setting in `meta` and never in the log. Match suggestions (`suggest` for folder files, `match_zotero` for Zotero items) are projections, never stored. `read_fulltext` checks the checksum before returning bytes. `fulltext_scope` defines which records need a full text (includes of the station feeding the `requires_fulltext` station; blind stages don't count). A station with `requires_fulltext` only gets retrieved records not assigned in an earlier round; the setup check `all_fulltext_status` gates it. `ZoteroLibraryLinked` and `ZoteroItemMapped` are lead-only.
- `highlights.rs`: highlights and comments in the full text; the PDF is never changed. `FullTextHighlightAdded` (`record_id`, `highlight` id, file `sha256`, `page`, `rects` as `[x, y, w, h]` in ten-thousandths of the page (`catalog::HIGHLIGHT_UNITS`, integers, zoom-independent), `text`, `color` from `catalog::HIGHLIGHT_COLORS`, `note`) and `FullTextHighlightRemoved` live in the stage chain (blindable) and are the only stage-chain events allowed in both screening and form stages (`catalog::is_highlight`, exception in `exchange::authorize`). A second `Added` with the same id from the same person replaces colour and note. `StageState.highlights` is keyed by record, person and id; `Review::highlights(record)` returns what the person may see across all stages (own always, others' only from stages that are not blind), with `editable` (own, stage open) and `stale` (checksum differs from the file now assigned). `add_highlight` needs write rights, an open stage and a retrieved full text; it does not require the record to be assigned, because a form stage assigns only the primary record of a bundle.
- `report.rs`: the report is a projection, nothing is stored. `Flow` holds the flow-diagram numbers: sources and duplicates from the log, then one `Level` per screening station with all its rounds (in the free template one per stage; sample stations like the pilot are no level). For a record the latest round it was assigned in counts; removed duplicates are left out; records in a blind-active stage count as `open` and their decisions appear nowhere. A level with `requires_fulltext` carries `Retrieval`. Records from imports with origin `citation` or `other` form the branch „andere Quellen“ (`other_identified`, per level `other_assessed`/`other_included`); they run through the same levels. `Flow::check` recomputes every level and returns what does not add up. `diagram_svg` renders the SVG in the core (text escaped, `currentColor`); `report_file` returns the files in `REPORT_FILES` (diagram, excluded full texts as CSV, included as RIS via `to_ris`, included sources with bundles as CSV, search appendix and methods text as Markdown). The exclusion reason of a record is the consensus reason, else the voters' common reason, else the first in criteria order (`StageState::exclusion_reason`). Exports of a single stage are projections too: `Review::stage_file` (screening, `csv` or `json`: decision, main reason and one vote per person; the JSON adds all reasons, notes and the consensus) and `Review::form_file` (`table`, `frequencies` as CSV, `json` with form, typed values per source and frequencies); both refuse while the stage is blind.
- `sources.rs`: `Studies` built from `RecordsLinkedToStudy` (study id, label, records, primary; an empty list dissolves; a later bundle takes a record out of an earlier one, and a bundle left with fewer than two records is gone) and `SourceTypeSet` (records + type, empty text clears). Both are lead-only main-chain events. `units` turns the included records of the last level (`Review::selection`) into sources: a bundle counts once, its type is the primary's. `Review::sources` is the view for the bundling tab; the report counts `included_sources` and `source_types` from the same units. Source types come from `Template.source_types`; without a list they are free text.
- `forms.rs`: `Forms` built from `FormVersionPublished` (form id, purpose `charting`/`appraisal`, versions with fields) and `FormConfirmed`; both lead-only. A field keeps its type across versions; once a form is confirmed, a new version needs a change note. A form stage is a `StageInstanceOpened` with `form_id` on a station of kind `form`; it assigns the primary record of each included source (`sources::units`), as a sample per source type for the pilot. `FormValueRecorded` and `FormEntryCompleted` live in the stage chain (blindable), `FormConsensusRecorded` in `main` (only after unblinding). `FormState::compare` gives each source a status (`open`, `extracted`, `conflict`, `incomplete`, `done`) for `unanimous` (double) or `single_verified` (one extracts, a second verifies via consensus values). Stages always use the newest form version; a completed entry missing a required field of that version is „nachzutragen“. Gate checks `form_confirmed`, `all_extracted`, `no_open_differences`. `exchange::authorize` checks values against the field of the version named in the event and keeps votes out of form stages and form events out of screening stages. `cast_vote` and friends reject form stages.
- `i18n.rs`: languages. `LANGUAGES` lists them; German is the source language, every other one is a catalogue `i18n/<code>.json` mapping the German text to its translation. `tr!("Text {}", x)` renders in the current language (literal on one line, only `{}`/`{0}`, no named or formatted placeholders), `i18n::text` looks up a whole text and leaves unknown ones untouched, `i18n::text_in(context, word)` prefers a catalogue entry „context: word“. The app sets the process language with `set_default` (command `language_set`); `with(code, …)` scopes one call on the current thread (report in another language, tests). **Language never enters the log**: never `tr!` anything that goes into a payload or table. Built-in templates are always logged in German; `Template::localized()`, `Template::term()` (terms sit under „Begriff: …“ in the catalogue, lowercase in English) and `Workflow::stations` translate for display only, so never write a localized view back. Tests `every_message_is_translated` (scans `tr!` literals in the core and `app/src-tauri`), `translations_take_the_same_values` and `workflow::template_texts_are_translated` keep the catalogues complete; all other tests run in German.
- `settings.rs`: settings on two levels, both local to this computer and never in the log or a package. `Settings` (program: language, output language, appearance, accent, decision palette, font size, density, screening layout, keyboard shortcuts, AI access in `Ai`: address, model, prompt template, publication details, plus endpoint path, extra request fields, answer pointer and timeout for APIs that differ, start folders for export and package dialogs) is the file `settings.json` in the app data dir (`load` falls back per value, `save` checks and replaces the file atomically); `ProjectSettings` (per review: label colour, plus optional overrides including the AI prompt, `None` = as in the program) is a JSON value under `meta` in the review file. `resolve` is the only place that merges both into `Effective`. Where reviews are stored is fixed and only shown. A new setting is a field with a default in the struct, its check, and its control in `SettingsPage.tsx`.
- `ai.rs`: AI suggestion for screening, without HTTP. `Review::ai_request` builds the prompt for one record of a screening stage from a template with the placeholders `{{review}}`, `{{questions}}` (registration answers `primary_questions`/`secondary_questions`), `{{criteria}}` (criteria of the stage), `{{record}}` (publication details only on request) and `{{format}}`; an empty template means `default_template()`, and a custom one without `{{record}}` or `{{format}}` gets them appended. The prompt texts follow the UI language and never enter the log, only `prompt_sha256` does. `parse` reads the answer leniently (code fences, `<think>` blocks, text around the JSON; an unknown reason is dropped). `record_ai_suggestion` appends `AiSuggestionReceived` (payload key `suggested`, not `decision`, so the reason rule for votes does not apply) and `resolve_ai_suggestion` appends `AiSuggestionResolved` (`accepted`/`declined`); both live in the stage chain and are therefore blindable. `StageState.suggestions` keeps the last suggestion per record and person in its own field; it never counts as a vote, in progress or in `final_decisions`. Accepting is a note; the vote itself is an ordinary `cast_vote`. The lead switches suggestions off or on for the whole review with `AiPolicySet` (`{allowed}`, main chain, lead-only; `Review::set_ai_policy`, `ReviewState::ai_allowed`); `ai_request` and `record_ai_suggestion` then refuse. `exchange::authorize` deliberately does not reject a suggestion made after the switch-off on a computer that had not received it yet (a rejected event would stop the stage chain and lose that person's votes); the methods text (`report::ai_text`) counts such suggestions via `ai_allowed_at` and states per station how many records, people, models and outcomes, never for a blind stage.
- `guidance.rs`: guideline summaries per built-in template (`guidance/<lang>/*.json`, embedded, one folder per language with identical structure; own words, source, access date and URL per entry). An entry names the template stations and UI areas (`AREAS`) it belongs to; `Guideline::check` validates that against the template and requires an entry for every screening and form station. Static content of the app version, never in the log. A new template needs its guideline file and an entry in `guidance::BUILTIN`.
- `registration.rs`: guided preparation of the registration. `registration/<lang>/osf_gsrrf.json` holds the 65 items of OSF's Generalized Systematic Review Registration form. `Review::registration_draft` returns each item with a suggestion computed from the review (projection, never stored) and the lead's own text; own texts are `ProtocolDrafted` events (main, lead-only; `{form, answers: {key: text}}`, last per key wins, empty text clears). `registration_markdown` is the export. The app never submits anything; after registering, the lead records `ProtocolRegistered`.
- `protocol.rs`: `Protocol` built from `ProtocolRegistered` (lead-only, main; the first event fixes the reference point, later ones only correct the details) plus the deviation list as a projection: criteria, search and workflow versions ≥ 2 after the reference point, form versions after confirmation and gate overrides always. `checklist` returns the PRISMA-ScR items (named in `Template.report.checklist`) with a computed status per item (`ready`, `open`, `manual`, `optional`) from an `Evidence` struct the report fills; nothing is stored. The report (`report.rs`) adds a section per form station to the methods text (`charting_text`, fed by `forms::StageSummary`), the table of included sources (`table_rows`, values of the last non-sample form station, latest round per source) and the files `table`, `deviations`, `checklist`. An update needs no event: new search version, import, further rounds; the live form check `all_sources_assigned` (`Facts.sources_without_round`) reopens the charting station while an included source sits in no round.
- Rounds: in a published template with fixed rounds, `open_stage` gives a further round only records not assigned in an earlier round of that station (late full texts, citation-search hits); samples draw anew. A `from_stage` scope whose source belongs to the station named in `input.station` takes the includes of all rounds of that station (latest decision per record), and so does `fulltext_scope`. The setup checks `citation_search_documented`, `all_records_assigned` and `source_types_set` gate the citation and bundling stations of the JBI template; their facts are only computed when the template asks.
- `agreement.rs`: percent, Cohen per pair + PABAK, Fleiss, Krippendorff, percentile bootstrap (ChaCha8, seed reported). Formulas mirror the former SQL functions; never report kappa alone.
- `service.rs` (`Review`): all business logic, a port of the former Django `services.py`. **Permissions and blinding are enforced here** (`require`, `blind_active` checks), not in the UI. `stage_records` feeds the screening list; while a stage is blind it rejects the filters for conflicts, other people and vote counts and reports them in `locked`. Errors are `error::Error` variants with German text (`Invalid`/`Forbidden`/`NotFound`/`Conflict`/`Integrity`).
- `exchange.rs`: `.ortid` identity files, `export_package` (blind filter per recipient), `export_return` (own events), `merge` (whole file rejected on bad hash/signature/unknown author; individual events rejected with a reason for gaps, missing rights, closed stages, consensus while blinded), `create_from_package`.
- `import.rs`: own RIS, BibTeX and PubMed (nbib) parsers, DOI normalisation, exact dedup key (DOI or normalised title + year).

**App** (`app/`): `src-tauri/src/commands.rs` holds thin `#[tauri::command]` wrappers that open the review file per call; `identity.rs` handles the Keychain, `ai.rs` sends the request built by the core to the configured OpenAI-compatible API (`ureq` with TLS, blocking inside `spawn_blocking`; the review file is closed while the model works) and reads the answer text at the configured JSON pointer; the API key is a second secret in `identity.rs` (`secret`/`set_secret`/`clear_secret`: Keychain account `ai-api-key`, with `ORT_KEY_STORE=file` the file `ai-api-key.key`), never in `settings.json` and never returned to the webview. `zotero.rs` reads Zotero's local API (`127.0.0.1:23119`, read-only, via `ureq`) and hands items to the core for matching. The review page's first tab („Ablauf“) renders stations from `ReviewDetail.workflow`; `NewReview.tsx` is the three-step creation wizard, `Criteria.tsx` the criteria view and editor, `Search.tsx` the search tab, `Duplicates.tsx` the pair view inside the import tab, `FullTexts.tsx` the full-text tab, `Sources.tsx` the bundling tab (bundles, primary record, source type), `Forms.tsx` the form tab (editor, versions, confirmation), `FormStage.tsx` the table of a form stage and the entry page next to the full text (routes `/reviews/:reviewId/forms/:stageId[/:recordId]`), `Guidance.tsx` the guideline tab and the `HelpButton` („?“ at the top right of every review screen, opening the entries for the open tab or the stage's station), `Registration.tsx` the guided registration dialog (one step per page of the OSF form, texts saved on blur), `Report.tsx` the report tab (shows the SVG from the core and saves files through `report_export`), `PdfView.tsx` the pdf.js reader (bytes come from the `fulltext_read` command; used in the tab, the screening page and the form entry page; with `marks` from `useHighlights` in `highlights.ts` it draws highlights as a layer above the text layer that takes no pointer events, turns a text selection into one rectangle per line, and opens a highlight by hit-testing the click position), `Screening.tsx` the three-column screening page (list with filters, record, criteria), `AiSuggestion.tsx` its AI dialog (`Modal` from `ui.tsx`: while open it owns the keys, Enter accepts, Esc declines) and the line showing the last suggestion. `i18n/index.ts` is the UI side of the languages: `t("Deutscher Text", {name})`, `tn` (plural), `tx` (elements inside a sentence), `capital` (template terms used as a label), `formatDate`/`formatNumber`/`formatPercent`; `i18n/en.ts` is the English catalogue and `t` only accepts keys present there, so a missing translation fails `npm run typecheck`. `main.tsx` only bootstraps: it loads the settings (`settings.ts`, which must not import `i18n` or `api`) and then imports `App.tsx` (shell, sidebar, routes), so the language is fixed before any module with texts loads (setting, else system language; changing it reloads) and `t` may be used in module-level constants; `App.tsx` passes it to the core before rendering. `settings.ts` holds the program settings and a cache of project settings, applies appearance, accent, palette, size and density as `data-*` attributes on the root element (`styles.css` reads them; font size is a `zoom` factor), and offers `useSettings`, `useProjectSettings`, `useScreeningLayout` and `inFolder`/`folder` (start folder of save and open dialogs). `SettingsPage.tsx` is the program page (route `/settings`, also the app menu entry with ⌘, which emits `open-settings`) and the review's „Einstellungen“ area. `shortcuts.ts` reads a shortcut from a key press (`shortcutOf`; a key with modifiers in fixed order, e.g. `Alt+M`; with Option or Shift the key comes from its position, since the browser then reports another character), compares (`hits`; while typing in a field only shortcuts with Ctrl or Cmd count) and displays it (`shortcutLabel`); the screening page (including the AI suggestion, `A` at first) and the focus mode take their keys from `Settings.shortcuts`, the digits 1–9 (reason) and `Esc` stay fixed. `focus.tsx` is the focus mode of the screening page and the form entry page (`useFocusMode`, `FocusButton`; shortcut from the settings, `F` at first, `Esc` leaves): it sets `data-focus` on the root element, `styles.css` hides sidebar, list and everything marked `focus-hide`, and the window goes full screen (Tauri window API in the app, the browser's in the preview); it ends when the page is left. Report and registration tabs take their output language from the review's settings (`outputLanguage(code)`, passed as `lang` to the commands) and save a change there. `dev/mock.ts` feeds the browser preview (`npx vite` in `app/`, then http://127.0.0.1:5173) and must follow the Rust types by hand. The React UI (`app/src/`) calls the commands via typed functions in `api.ts` (camelCase args) and uses `@tauri-apps/plugin-dialog` for file pickers. The webview never touches files itself. Routing is `HashRouter`; routes carry both `reviewId` and `stageId`. Inside a review the sidebar (`App.tsx`) lists the review's areas from `shared.ts` (`REVIEW_TABS`) instead of the review list (reachable via „Alle Reviews“) and, indented under „Ablauf“, the review's stages (the review page shares them with the shell after every load, on stage pages the shell loads them itself); the open area is the `?tab=` query parameter of the review route.

**Tests**: `crates/ort-core/tests/common/mod.rs` builds a `Team` (owner, two reviewers, viewer) with separate files that only talk through `wire()`-serialised bundles. `flow.rs` is the end-to-end scenario; `exchange.rs` covers tampering and rejection cases; `workflow.rs` covers templates, gates, decision rules, required reasons, criteria versions per stage, list filters, the search and duplicate gates, full texts (rounds, checksum, folder per person), the report (adds up at every step, blind decisions stay out), the citation search as a second pass with bundling, charting (blind, differences only after unblinding, form change after the pilot, single extraction with verification, rejection on merge), the update with protocol, deviations, checklist and table, the registration draft (suggestions, own texts, rejection on merge), the language switch (display changes, the log does not), project settings (no event, nothing in a package), AI suggestions (prompt from the review's data, blind while the stage is blind, never a vote; switched off by the lead and named in the methods text), full-text highlights (blind, own only editable, stale after a new file, allowed in form stages), and runs the same walk with every built-in template (`walk`, which names no station key; `Team::with_template`). The UI has no automated tests (Tauri has no WebDriver on macOS).
